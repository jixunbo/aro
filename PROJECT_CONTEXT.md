# Project context

## Purpose and current capabilities

aro (Everything Around You) is a privacy-first combined iOS/iPadOS and watchOS app. The surviving `aro` iOS host records a user's location history with selectable power/accuracy trade-offs, while its embedded watchOS companion reports Apple Watch battery and device state to the iPhone dashboard and Shortcuts. The app can record location in the background, show today's route and per-day history, render a sampled lifetime overview, calculate distance and point counts, import/export GPX and GeoJSON, delete track data, display the latest watch battery snapshot, manually refresh it when reachable, provide the “获取设备电量” App Intent, and expose Watch-face complications for both Watch battery and today's route/distance. Track data always has a local SQLite copy; iCloud sync is an explicit opt-in using the user's private CloudKit database and a compile-time optional capability. Local builds remain fully functional without CloudKit. The app has no aro account, self-hosted backend, analytics, or third-party service API.

## Architecture and data flow

- The SwiftUI iOS app uses an `AppDelegate` to distinguish location-triggered cold launches from ordinary/remote-notification launches. Location-triggered launches initialize `LocationService` but deliberately skip CloudKit and WatchConnectivity startup so background location does not gain incidental network/device work. When iCloud sync is enabled, ordinary launch and scene activation start or resume the sync engine early enough for CloudKit remote-notification delivery; ordinary launch and foreground activation also passively activate WatchConnectivity so queued application context can be ingested without sending a live battery request.
- Onboarding stages When In Use and Always location authorization; the main UI has Today, History, Insights, Devices, and Settings tabs.
- `LocationService` owns two `CLLocationManager` instances. One monitors significant location changes and visits for low-power wakeups; the other supplies standard updates in Balanced, Precise, and Workout modes. Motion activity labels samples and selects an appropriate Core Location activity type while detail updates are active. Balanced and Precise let Core Location automatically pause standard updates rather than manually degrading them to kilometer accuracy; when a pause occurs, motion updates stop, and a later significant-location or visit-departure wake explicitly restarts the standard location service.
- Incoming locations pass through `TrackMath` accuracy, freshness, duplicate, time-order, and implausible-speed filters before insertion. Accepted points include their source and current motion label.
- `TrackDatabase` owns the SQLite connection and serializes access on a utility queue. `TrackRepository` moves reads to detached tasks and publishes view state on the main actor. The UI does not query SQLite directly except for Settings' detached full export/import work.
- Each stored track point has a stable `sync_id` plus local `cloud_synced` bookkeeping. Existing databases are migrated in place and backfilled with IDs. Local recording/import writes remain local-first and unsynced; remote CloudKit points are applied transactionally and rebuild summaries when new rows are inserted. If an incoming remote point collides with an unsynced local row on the existing timestamp/latitude/longitude natural key, the local row adopts the remote `sync_id` and is marked synced instead of uploading a duplicate record.
- `CloudTrackSyncEngine` wraps `CKSyncEngine` against the private database of `iCloud.com.xunbo.aro`, using a custom `AROTracks` zone and `TrackPoint` records. CKSyncEngine state is persisted under `Application Support/traceon/cloudkit-sync-state.json`. SQLite remains the local source of truth and `daily_summary` is never uploaded; remote raw-point changes are imported/deleted locally and summaries are derived again.
- `CloudSyncService` exposes opt-in state, status, last-sync time, manual sync, and destructive cloud/local deletion to Settings. Disabling sync stops the engine but intentionally does not delete existing CloudKit data. “Delete all tracks” deletes the CloudKit zone first whenever the app knows a cloud footprint exists, then clears local SQLite. A zone deletion fetched from another synced device is treated as a global delete and clears the local tracks too, preventing stale local data from being re-uploaded.
- CloudKit is a compile-time optional capability. Local `Debug`/`Release` builds omit the CloudKit/APNs entitlements and compile out the CloudKit service, while `CloudDebug`/`CloudRelease` retain the existing private-container and remote-notification behavior. The local UI explicitly marks iCloud sync as unavailable; this switch does not change SQLite, Core Location, WatchConnectivity, Watch App, or Widget behavior.
- `TrackMapView` bridges SwiftUI to `MKMapView`, splits routes at long gaps or impossible jumps, renders native gradient polylines, and lets users inspect the nearest recorded timestamp by tapping a route.
- GPX import/export preserves coordinates, elevation, and available timestamps. GeoJSON handles `LineString` and `MultiLineString` imports and exports a `FeatureCollection` containing one `LineString`.
- The Devices feature remains separate from location/data ownership. `BatterySnapshot.swift` is compiled into iOS, Watch App, and Widget targets and defines both the Watch battery payload and the compact `TrackComplicationSnapshot` transport type. The watch is the battery source; it publishes its latest battery snapshot through application context and can reply to explicit reachable messages. `BatteryStore` caches the newest valid timestamped battery snapshot in iOS `UserDefaults` under `latestAppleWatchBatterySnapshot`.
- For the route complication, the iPhone remains the only track source. `TrackMath.trackComplicationSnapshot` filters to the current local day, keeps cumulative distance, splits the route using the same long-gap/impossible-speed concept as map display, keeps at most the latest four display segments, downsamples each to at most eight points, projects longitude using mean latitude, preserves aspect ratio, and normalizes the route into a unit square for small Watch rendering.
- `PhoneConnectivity` owns outbound route publication without being driven by `LocationService`. `RootView` queues the newest route whenever `TrackRepository.todayPoints` changes and on ordinary foreground activation. `publishTrackComplication` never activates WatchConnectivity itself: if the session does not already exist/activate, it only retains the latest in-memory snapshot. Foreground activation flushes immediately; while an already-active session survives in the background, application-context publication is throttled to five minutes or 250 metres of distance change, with new-day/first-route state allowed immediately. This preserves Core Location cold-launch isolation while letting normal background recording opportunistically refresh the Watch face.
- The watch app persists the newest `BatterySnapshot` and newest current-day `TrackComplicationSnapshot` in the Watch App Group `group.com.xunbo.traceon.watch`. The Widget bundle exposes two kinds: the stable legacy battery kind and the new `AROTrackWidget`. The circular battery complication uses an Ultra-style gauge with tick marks and an orange normal-state accent (green while charging/full, red when low); existing battery corner/inline/rectangular families remain available. The track complication currently supports accessory-circular only and draws the transmitted mini route plus cumulative distance. Track WidgetKit does not start Core Location on the watch.
- A WidgetKit battery timeline refresh still takes one local `WKInterfaceDevice` battery sample, persists it to the same newest-timestamp-wins store, and returns it in the new timeline. This system-budgeted fallback has no timer, network request, or iPhone wake and keeps the battery complication useful when watchOS does not deliver the watch app's requested background refresh. `WatchBatteryService` remains responsible for Watch App UI and WatchConnectivity battery publication, and reloads the battery complication only when displayed battery/status values change. It also receives the iPhone's track application context, saves newer route snapshots, and reloads only the track complication when route/distance changed.
- The original battery WidgetKit kind string remains stable so an installed battery complication survives the display-name rename; a WatchConnectivity `sendMessage` is reserved for an explicit iPhone battery request/reply. Track data uses application context only and never sends an unsolicited live message.
- `PhoneConnectivity` is main-actor isolated and passive. Ordinary iPhone launch and foreground activation may activate the session and accept queued application-context battery snapshots, but activation itself never requests live battery data. Live battery requests occur only when the Devices tab is selected/refreshed or the App Intent runs. It has no polling timer or iPhone background task, is not coupled to `LocationService`, and is deliberately skipped during a Core Location-triggered cold launch.
- The watch app samples battery on activation, every five minutes only while its scene is active, when leaving the foreground, during watchOS-scheduled application refresh, and in response to an explicit reachable iPhone request. Each one-shot read enables battery monitoring only for the sampling window and disables it immediately afterward. Repeated foreground samples persist their timestamp locally but publish WatchConnectivity application context only when the displayed battery, charge state, or device name changes. Scheduled refresh uses the single-target watch app's `WKApplicationDelegate.handle(_:)` and `WKApplication.scheduleBackgroundRefresh`, schedules the next task before sampling, awaits the battery read, and explicitly completes every delivered WatchKit background task. The preferred next app refresh is one hour; the battery Widget requests a new timeline after 30 minutes. Both intervals remain system-controlled and are not guaranteed. The Watch App opts out of Always On display so leaving the active scene does not keep aro visible on the dimmed screen.

## Storage

- The database is `Application Support/traceon/tracks.sqlite3`, uses SQLite WAL with `synchronous=NORMAL`, and is protected until the first device unlock.
- `track_points` stores raw samples plus `sync_id` and `cloud_synced`. A unique index on timestamp, latitude, and longitude provides import/recording deduplication; a unique index on `sync_id` provides CloudKit identity. `daily_summary` stores per-local-calendar-day point counts, distance, and first/last timestamps for history and lifetime statistics.
- Normal inserts increment the relevant daily summary. Batch imports and remote CloudKit changes rebuild summaries when necessary from timestamp-ordered raw points.
- Today/day queries are capped at 50,000 points; the lifetime map reads at most 8,000 sampled points while preserving the oldest and newest endpoints. Full export reads all points.
- Tracking enabled state, tracking mode, onboarding completion, iCloud opt-in/status bookkeeping, and the iPhone Watch battery cache are in standard `UserDefaults`. CloudKit sync state is stored separately as a serialized CKSyncEngine state file. Watch battery and track-complication snapshots use the Watch App Group store shared only between the Watch App and Widget Extension.
- When no CloudKit footprint exists, deleting all data clears both SQLite tables locally. If a CloudKit footprint may exist, deletion must remove the private `AROTracks` zone before clearing local SQLite so another device cannot restore the deleted history. Uninstalling the app still removes the local container but does not by itself delete CloudKit data.
- The user-visible name is aro and the product bundle identifiers use the aro namespace: iOS `com.xunbo.aro`, Watch App `com.xunbo.aro.watchkitapp`, and Widget Extension `com.xunbo.aro.watchkitapp.widget`. These identifiers intentionally create a new app identity; an existing Traceon/Companio install does not receive an in-place upgrade or automatic SQLite/UserDefaults migration. The database path remains `Application Support/traceon/tracks.sqlite3` within the new container, and the watch snapshot cache remains independent of the SQLite track database.

## Runtime and dependencies

- Minimum deployment targets: iOS/iPadOS 17.0 and watchOS 10.0. The iOS target supports iPhone and iPad, not Mac Catalyst.
- The project has four targets: `aro` (`com.xunbo.aro`), embedded `ARO Watch App` (`com.xunbo.aro.watchkitapp`, companion identifier `com.xunbo.aro`), embedded `ARO Watch Widget Extension` (`com.xunbo.aro.watchkitapp.widget`), and `aroTests`. The shipped iOS, Watch App, and Widget display name is `aro`; the Watch App and Widget Extension share the stable Watch App Group `group.com.xunbo.traceon.watch`; the iOS host does not need that group.
- The repository and Xcode project are named `aro` (`aro.xcodeproj`); the former Traceon/Companio names remain only in the stable data path, WidgetKit battery kind, App Group, or historical upgrade notes.
- Project settings use Swift 5 with minimal strict-concurrency checking. `README.md` requires Xcode 26+; the project was last created/upgraded with Xcode 26.3.
- Every user-visible change or bug fix must include an appropriate semantic marketing-version bump before delivery: patch for fixes, minor for backward-compatible features, and major for breaking changes. Keep the iOS App, Watch App, Widget Extension, and all Local/Cloud configurations on the same marketing version. The current version is `1.4.3`; the Watch App reads its installed marketing/build versions from its bundle and displays them at the bottom of the main screen.
- Dependencies are Apple frameworks plus the system SQLite library linked with `-lsqlite3`. Cloud sync uses CloudKit/CKSyncEngine; the device feature uses WatchConnectivity, WatchKit, WidgetKit, WatchKit background tasks, and AppIntents. There are no package-manager dependencies or external service APIs.
- The app declares `location` and `remote-notification` background modes. Local `Debug`/`Release` use `aro/aro.local.entitlements`, which is empty and does not require CloudKit or Push Notifications; `CloudDebug`/`CloudRelease` use `aro/aro.entitlements` with container `iCloud.com.xunbo.aro` and APNs development entitlement. Cloud real-device signing requires an Apple Developer Program team and matching iCloud/CloudKit and Push Notifications capabilities. Watch App and Widget configurations always keep only `group.com.xunbo.traceon.watch`.

## Known limitations

- iOS schedules background location delivery. Even with Always authorization, significant-change and visit monitoring do not guarantee a continuous, point-by-point route after suspension or termination. After an automatic standard-location pause, the first low-power wake may itself require a meaningful movement before detailed updates restart.
- Local/Cloud compile separation can be validated in CI, but CloudKit behavior cannot be validated by unsigned CI builds or simulator alone. Push-driven multi-device sync, provisioning/capabilities, account transitions, zone deletion propagation, and energy effects require the Cloud real-device checks in `TESTING.md`; Personal Team installation and local iCloud-unavailable UI require the Local checks there.
- iCloud account switching is intentionally conservative: sync is disabled and local rows are marked unsynced. Cloud data belonging to the previous Apple account remains in that previous account until the user switches back and deletes it there.
- If two devices have already uploaded the same natural track point under different historical `sync_id` values, CloudKit can contain redundant records even though SQLite deduplicates them locally. The implemented reconciliation prevents the common case where an unsynced local duplicate first encounters an existing cloud record before upload.
- GeoJSON export contains no timestamps, and GeoJSON import assigns points sequential timestamps starting at import time. A GeoJSON round trip therefore changes dates and timing.
- GPX points without a timestamp also receive import-time sequential fallback timestamps.
- Full export and daily-summary rebuild load the complete point history into memory. Large-history behavior has no dedicated automated test.
- Unit tests cover filtering, distance, GPX import, GPX/GeoJSON export, lifetime-overview SQLite sampling, sync-ID migration/bookkeeping, remote duplicate reconciliation, cloud-driven record deletion, track-complication payload encoding, and normalized route projection/splitting at the database/math layer. Broader authorization transitions, background relaunch, timezone/DST grouping, CloudKit delivery, and energy use remain dependent on manual or real-device validation in `TESTING.md`.
- iOS cannot read Apple Watch battery through a public API. The companion must be installed and opened at least once; when it is unreachable, the UI and App Intent return the latest timestamped cache rather than guaranteed live state.
- WatchConnectivity delivery and watchOS background refresh timing are system-controlled. The active battery complication increases the watch app's opportunity to receive background refresh budget and provides direct watch-face visibility, but does not guarantee a fixed interval. Simulator compilation does not validate paired-device transfer, complication scheduling, Shortcut results, background refresh, CloudKit pushes, or the combined app's real-world energy impact.
- The track complication is not a second GPS recorder and is not guaranteed real time. It can update immediately on normal foreground synchronization and opportunistically while an already-active WatchConnectivity session survives in the background, but location-only cold launches do not activate connectivity. watchOS may coalesce application context, so the mini route can lag the iPhone track. It currently supports accessory-circular only and displays at most four recent route segments with eight sampled points per segment.
