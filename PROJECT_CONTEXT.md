# Project context

## Purpose and current capabilities

aro (Everything Around You) is a privacy-first combined iOS/iPadOS and watchOS app. The `aro` iOS host records a user's location history with selectable power/accuracy trade-offs, while its embedded watchOS companion reports Apple Watch battery and device state to the iPhone dashboard and Shortcuts. The app can record location in the background, show today's route and per-day history, render a sampled lifetime overview, calculate distance and point counts, import/export GPX and GeoJSON, delete track data, display the latest watch battery snapshot, manually refresh it when reachable, provide the “获取设备电量” App Intent, and expose Watch-face complications for both Watch battery and today's route/distance. Track data always has a local SQLite copy; iCloud sync is an explicit opt-in using the user's private CloudKit database and a compile-time optional capability. Local builds remain fully functional without CloudKit. The app has no aro account, self-hosted backend, analytics, or third-party service API.

Current unreleased marketing version: **2.0.2**.

aro 2.0 intentionally requires iOS/iPadOS 26.0 or later. There is no iOS 17–25 location compatibility layer.

## Architecture and data flow

### iOS application lifecycle

- The SwiftUI app uses `AppDelegate` only for process-level service restoration. iOS 26 deprecates the old `UIApplication.LaunchOptionsKey.location` discriminator, so aro no longer branches on that launch option.
- `AppDelegate.application(_:didFinishLaunchingWithOptions:)` immediately restores `LocationService` if tracking was already enabled. It deliberately does not activate WatchConnectivity or CloudKit. This is safe for a Core Location background relaunch because location remains the only launch-time subsystem.
- Normal foreground lifecycle is owned by `RootView`: it refreshes repository state, updates App Shortcuts, passively activates WatchConnectivity, publishes the latest route snapshot, and in Cloud builds resumes CloudKit. CloudKit remote notifications use their own `UIApplicationDelegate` callback and call the cloud sync service explicitly.
- Onboarding stages When In Use and Always authorization. aro 2.0 starts automatic all-day recording only with `authorizedAlways`; it does not run a degraded When-In-Use tracking fallback.

### iOS 26 location engine

- `LocationService` is a main-actor state owner. It keeps one `CLLocationManager`. In Eco this manager is the actual Standard location recorder; in the other modes it is used only for authorization/full-accuracy state while route production comes from Live Updates.
- All automatic recording modes hold an explicit `CLServiceSession(authorization: .always)`. `NSLocationRequireExplicitServiceSession` is enabled so location authorization intent is explicit and tied to the tracking feature.
- Eco is intentionally different from the other modes. It uses Standard Core Location with `kCLLocationAccuracyNearestTenMeters`, about a 100 m `distanceFilter`, automatic pausing, background updates allowed, and no `CLBackgroundActivitySession`. This moves the primary Eco energy control to Core Location's update-generation layer instead of receiving many fixes and discarding them in SQLite policy.
- Balanced uses `CLLocationUpdate.liveUpdates(.default)` without `CLBackgroundActivitySession`. Precise uses `.otherNavigation` and Workout uses `.fitness`; those two retain a `CLBackgroundActivitySession` because they explicitly trade more energy for timely background delivery.
- The tracking-enabled state, selected mode, `tracking.startedAt` timestamp, local recorder anchor, and whether aro expects its idle monitor to be armed are persisted in `UserDefaults`. The session-start timestamp marks the lower bound of the current tracking session. An upgrade from 1.x creates a new boundary instead of treating arbitrary legacy cached fixes as queued 2.0 work.
- Real-device 2.0 testing showed `.default` Live Updates could continue producing hundreds of accurate fixes during more than 30 minutes of physical inactivity without ever emitting `stationary`. `CLLocationUpdate.isStationary` is therefore useful when it appears but is not trusted as Balanced's sole idle signal.
- Balanced maintains a rolling window of fresh, sufficiently accurate Live Updates. Its idle detector uses a median center, requires about five minutes of history and at least 90% of samples inside roughly 30 m, and also requires the robust early/late cluster centers to drift no more than about 20 m. This lets one or two GPS outliers through without letting a slowly translating route masquerade as stationary.
- Eco normally reaches idle through `CLLocationManager` automatic pause. On the pause callback, aro uses the latest reliable location to arm one persistent roughly 100 m `CLMonitor.CircularGeographicCondition`, then explicitly stops Standard updates. Balanced arms a roughly 60 m condition after its robust spatial idle proof. A native Live Updates stationary fix can enter Balanced's same monitor path immediately.
- Leaving the monitored circle is the normal wake path for Eco/Balanced: remove the condition, reset transient geometry/idle state, and resume the mode's own primary recorder (Eco Standard distance-filtered updates, Balanced Live Updates). `CLMonitor` is a first-class idle state, not a route-producing fallback.
- On process relaunch, if `tracking.idleMonitorActive` is set, aro recreates the named `CLMonitor` and checks its persistent identifier. If the identifier exists, it awaits monitor events without starting the moving recorder; if it is absent, aro clears the flag and resumes the mode's primary recorder.
- Significant-location-change monitoring, visit monitoring, Eco GPS bursts, and Core Motion wake logic are not part of the recorder. No legacy wake path is used.
- Switching tracking mode tears down an armed idle condition if necessary, updates background-delivery policy, stops the previous primary recorder, and starts the new mode's recorder. The explicit Always service session remains scoped to the overall tracking feature.
- Settings exposes current engine state, selected background policy, latest horizontal accuracy, and process-local counts of update events, updates containing a location, persisted locations, and filtered locations. A non-stationary Core Location event is no longer presented as proof that the user is moving; the UI stays at `监测中` until meaningful displacement exists.

### Location acceptance and route sampling

- `TrackMath.shouldRecordLiveLocation` is shared by Live Updates and Eco Standard callbacks. A candidate must have a valid coordinate, nonnegative horizontal accuracy no worse than the selected mode's ceiling, a timestamp at or after the persisted current tracking-session boundary, no more than 60 seconds in the future, and a timestamp newer than the previously persisted point in the same tracking session.
- The old 180-second wall-clock freshness filter is intentionally gone. iOS can queue valid callbacks while the process is suspended and deliver them later; current-session queued points must remain eligible even if they are several minutes old.
- Implausible short-interval motion faster than 100 m/s is rejected. Movements below five metres are treated as duplicates/noise.
- Sampling uses an accuracy-aware noise radius based on half of the worse horizontal accuracy of adjacent saved fixes. A point is persisted when it exceeds the mode's normal distance threshold, when enough time has elapsed and there has still been meaningful movement, or when a genuine turn is detected after enough movement.
- Eco's hardware cadence is approximately 100 m because of `distanceFilter`; its storage gate is intentionally lower (25 m, 50 m maximum accepted horizontal accuracy) so useful extra system-delivered fixes are not discarded. The resulting point spacing should usually be near the system distance filter rather than a second 100 m software gate.
- Balanced accepts fixes up to 80 m horizontal accuracy, uses about 35 m normal persistence distance, a one-minute maximum persistence interval with at least 12 m movement, and can preserve turns after about 12 m if direction changes by at least 35 degrees.
- `TrackMath.idleMonitorCenter` is used only for Balanced spatial idle detection. It requires a fresh newest fix, a full-duration window, a high inlier fraction around a robust median center, and limited early-to-late center drift. This prevents delayed queued locations from immediately putting a newly resumed moving device back to sleep and prevents isolated GPS spikes from keeping a truly stationary device awake forever.
- Turn detection does not rely solely on `CLLocation.course`. `LocationService` keeps a small in-memory geometry history from sufficiently separated good locations and derives path bearings; `TrackMath.headingDifference` uses that observed turn when available, with valid Core Location course still usable as an additional native signal. Geometry and idle-detection state reset on tracking/mode/wake transitions.
- Accepted Live Updates use source `live`; Eco Standard points use source `standard`. Legacy source strings remain displayable for historical data.

### Database and synchronization

- `TrackDatabase` owns the SQLite connection and serializes access on a utility queue. `TrackRepository` moves reads to detached tasks and publishes view state on the main actor. The UI does not query SQLite directly except for Settings' detached full export/import work.
- Each stored track point has a stable `sync_id` plus local `cloud_synced` bookkeeping. Existing databases are migrated in place and backfilled with IDs. Local recording/import writes remain local-first and unsynced; remote CloudKit points are applied transactionally and rebuild summaries when new rows are inserted. If an incoming remote point collides with an unsynced local row on the existing timestamp/latitude/longitude natural key, the local row adopts the remote `sync_id` and is marked synced instead of uploading a duplicate record.
- `CloudTrackSyncEngine` wraps `CKSyncEngine` against the private database of `iCloud.com.xunbo.aro`, using a custom `AROTracks` zone and `TrackPoint` records. CKSyncEngine state is persisted under `Application Support/traceon/cloudkit-sync-state.json`. SQLite remains the local source of truth and `daily_summary` is never uploaded; remote raw-point changes are imported/deleted locally and summaries are derived again.
- `CloudSyncService` exposes opt-in state, status, last-sync time, manual sync, and destructive cloud/local deletion to Settings. Disabling sync stops the engine but intentionally does not delete existing CloudKit data. “Delete all tracks” deletes the CloudKit zone first whenever the app knows a cloud footprint exists, then clears local SQLite. A zone deletion fetched from another synced device is treated as a global delete and clears the local tracks too, preventing stale local data from being re-uploaded.
- CloudKit is a compile-time optional capability. Local `Debug`/`Release` builds omit CloudKit/APNs entitlements and compile out the CloudKit service, while `CloudDebug`/`CloudRelease` retain private-container and remote-notification behavior. CI compiles both `Debug` and `CloudDebug` so code behind `ARO_CLOUDKIT_ENABLED` is compile-checked.
- `TrackMapView` bridges SwiftUI to `MKMapView`, splits routes at long gaps or impossible jumps, renders native gradient polylines, and lets users inspect the nearest recorded timestamp by tapping a route.
- GPX import/export preserves coordinates, elevation, and available timestamps. GeoJSON handles `LineString` and `MultiLineString` imports and exports a `FeatureCollection` containing one `LineString`.

### Apple Watch and device data

- The Devices feature remains separate from location/data ownership. `BatterySnapshot.swift` is compiled into iOS, Watch App, and Widget targets and defines both the Watch battery payload and the compact `TrackComplicationSnapshot` transport type. The watch is the battery source; it publishes its latest battery snapshot through application context and can reply to explicit reachable messages. `BatteryStore` caches the newest valid timestamped battery snapshot in iOS `UserDefaults` under `latestAppleWatchBatterySnapshot`.
- For the route complication, the iPhone remains the only track source. `TrackMath.trackComplicationSnapshot` filters to the current local day, keeps cumulative distance, splits the route using the same long-gap/impossible-speed concept as map display, keeps at most the latest four display segments, downsamples each to at most eight points, projects longitude using mean latitude, preserves aspect ratio, and normalizes the route into a unit square for small Watch rendering.
- `PhoneConnectivity` owns outbound route publication without being driven by `LocationService`. `RootView` queues the newest route whenever `TrackRepository.todayPoints` changes and on ordinary foreground activation. `publishTrackComplication` never activates WatchConnectivity itself: if the session does not already exist/activate, it only retains the latest in-memory snapshot. Foreground activation flushes immediately; while an already-active session survives in the background, application-context publication is throttled to five minutes or 250 metres of distance change, with new-day/first-route state allowed immediately. When the Watch reports an active complication and system complication-transfer budget is available, the iPhone also uses `transferCurrentComplicationUserInfo` for route changes; the Watch handles both application-context and complication-user-info delivery and reloads the track WidgetKit timeline after persistence.
- A location-only process relaunch does not activate WatchConnectivity. This preserves the low-power boundary even though accepted background points can still refresh `TrackRepository` and opportunistically publish only if a WatchConnectivity session was already active.
- The watch app persists the newest `BatterySnapshot` and newest current-day `TrackComplicationSnapshot` in Watch App Group `group.com.xunbo.traceon.watch`. The Widget bundle exposes the stable battery kind plus `AROTrackWidget`. The circular battery complication uses an Ultra-style gauge with green above 50%, orange from 21–50%, red at 20% or below, and charging/full always green. Battery sampling uses the public `WKInterfaceDevice.batteryLevel`; watchOS does not expose another public API that guarantees finer percentage granularity. The track complication currently supports accessory-circular only and draws the transmitted mini route plus cumulative distance. Track WidgetKit never starts Core Location on the watch.
- A WidgetKit battery timeline refresh takes one local `WKInterfaceDevice` battery sample, persists it to the same newest-timestamp-wins store, and returns it in the new timeline. This system-budgeted fallback has no timer, network request, or iPhone wake. `WatchBatteryService` remains responsible for Watch App UI and WatchConnectivity battery publication.
- `PhoneConnectivity` is main-actor isolated and passive. Live battery requests occur only when the Devices tab is selected/refreshed or the App Intent runs. It has no polling timer or iPhone background task and is not coupled to `LocationService`.
- The watch app samples battery on activation, every five minutes only while its scene is active, when leaving the foreground, during watchOS-scheduled application refresh, and in response to an explicit reachable iPhone request. Each one-shot read enables battery monitoring only for the sampling window and disables it immediately afterward. The preferred next app refresh is one hour; the battery Widget requests a new timeline after 30 minutes. Both are system-controlled and not guaranteed. The Watch App opts out of Always On display.

## Storage

- The database is `Application Support/traceon/tracks.sqlite3`, uses SQLite WAL with `synchronous=NORMAL`, and is protected until the first device unlock.
- `track_points` stores raw samples plus `sync_id` and `cloud_synced`. A unique index on timestamp, latitude, and longitude provides import/recording deduplication; a unique index on `sync_id` provides CloudKit identity. `daily_summary` stores per-local-calendar-day point counts, distance, and first/last timestamps for history and lifetime statistics.
- Normal in-order inserts increment the relevant daily summary. If a valid queued recorded point arrives older than the database's current latest point, the summary is rebuilt from timestamp-ordered raw points so history/lifetime distance stays consistent. Batch imports and remote CloudKit changes also rebuild summaries when necessary.
- Today/day queries are capped at 50,000 points; the lifetime map reads at most 8,000 sampled points while preserving the oldest and newest endpoints. Full export reads all points.
- Tracking enabled state, tracking mode, modern tracking-session start timestamp, persisted local recorder anchor, `tracking.idleMonitorActive`, onboarding completion, iCloud opt-in/status bookkeeping, and the iPhone Watch battery cache are in standard `UserDefaults`. Core Location owns the persistent CLMonitor condition itself; the boolean only tells aro which engine state to restore. CloudKit sync state is stored separately as a serialized CKSyncEngine state file. Watch battery and track-complication snapshots use the Watch App Group shared only between Watch App and Widget Extension.
- When no CloudKit footprint exists, deleting all data clears both SQLite tables locally and clears/restarts the recorder anchor/session state so a deleted point cannot filter future locations. If a CloudKit footprint may exist, deletion must remove the private `AROTracks` zone before clearing local SQLite so another device cannot restore deleted history. Uninstalling the app removes the local container but does not by itself delete CloudKit data.
- The user-visible name is aro and bundle identifiers use the aro namespace: iOS `com.xunbo.aro`, Watch App `com.xunbo.aro.watchkitapp`, Widget Extension `com.xunbo.aro.watchkitapp.widget`. Existing Traceon/Companio containers are not automatically visible to aro. The database path remains `Application Support/traceon/tracks.sqlite3` inside the aro container.

## Runtime and dependencies

- Minimum deployment targets: iOS/iPadOS 26.0 and watchOS 10.0. The iOS target supports iPhone and iPad, not Mac Catalyst. iOS 27 is expected to be supported through the same minimum-target build; there is no maximum OS gate.
- The project has four targets: `aro`, embedded `ARO Watch App`, embedded `ARO Watch Widget Extension`, and `aroTests`. Shipped iOS, Watch App, and Widget display name is `aro`.
- Project settings use Swift 5 with minimal strict-concurrency checking. Xcode 26+ is required; the project was last created/upgraded with Xcode 26.3.
- aro 2.0.2 is the current unreleased 2.0 line. The iOS App, Watch App, Widget Extension, and all Local/Cloud configurations keep the same marketing version. The Watch App reads its installed marketing/build versions from its bundle.
- Dependencies are Apple frameworks plus system SQLite (`-lsqlite3`). Core Location uses Standard location updates for Eco, Live Updates for Balanced/Precise/Workout, service/background activity sessions, and CLMonitor; Cloud sync uses CloudKit/CKSyncEngine; device functionality uses WatchConnectivity, WatchKit, WidgetKit, WatchKit background tasks, and AppIntents. There are no package-manager dependencies or external service APIs.
- The iOS app declares `location` and `remote-notification` background modes. Local `Debug`/`Release` use `aro/aro.local.entitlements`; `CloudDebug`/`CloudRelease` use `aro/aro.entitlements` with `iCloud.com.xunbo.aro` and APNs development entitlement. Watch App and Widget configurations keep only `group.com.xunbo.traceon.watch`.

## Known limitations and validation boundaries

- Simulator/build tests cannot prove Standard-location automatic pause timing, CLMonitor boundary wake timing, Core Location suspension, process relaunch, queued delivery, or battery behavior. Those require iOS 26 real-device checks in `TESTING.md`.
- Eco intentionally depends on Standard Core Location's `distanceFilter ≈ 100 m` plus automatic pause. Apple documents the distance filter as the minimum horizontal movement before an update event is generated, but the system may still provide startup or improved-accuracy fixes. Real-device comparison must therefore look at the distribution of point spacing rather than expect exactly 100.0 m.
- Eco's inferred competitor-like behavior is an engineering approximation based on exported route data and public iOS APIs; the competitor's private implementation is unknown. The release gate is similar route density/accuracy and stationary power behavior, not byte-for-byte behavior.
- Balanced idle tuning is currently ~5 minutes with a robust 90% inlier rule inside 30 m, limited early/late center drift, followed by a 60 m monitored circle. The release gate is that stationary power improves materially without recreating the 1.5 failure where the first several hundred metres after movement were missing.
- Precise/Workout keep a timely background activity session and do not enter the idle monitor path; their greater battery cost is intentional.
- The current Balanced route thresholds (80 m max accuracy, ~35 m normal persistence, one-minute timed persistence with 12 m movement, turn-aware early points) are based on the 1.5 failure plus first 2.0 diagnostics but still require same-route real-device comparison.
- Unit tests cover current-session queued-location acceptance, pre-session/future/inaccurate rejection, near-duplicate and impossible-speed filtering, normal/timed/turn-aware persistence, robust stable/outlier/moving/stale idle-window classification, geometric bearings, Eco Standard distance-filter policy, mode background/idle policy, distance, GPX import/export, GeoJSON export, lifetime-overview SQLite sampling, out-of-order summary rebuilding, sync bookkeeping, CloudKit duplicate reconciliation/deletion, and Watch track snapshot projection/splitting. Standard automatic pause, CLMonitor lifecycle and energy remain real-device concerns.
- Local/Cloud compile separation is validated in CI, but signed CloudKit silent push, provisioning, multi-device sync, account changes, and energy effects require real devices.
- iCloud account switching is intentionally conservative: sync is disabled and local rows are marked unsynced. Cloud data belonging to the previous Apple account remains there until the user switches back and deletes it.
- GeoJSON export contains no timestamps, and GeoJSON import assigns sequential timestamps starting at import time. GPX points without timestamps also receive import-time fallback timestamps.
- Full export and daily-summary rebuild load the complete point history into memory. Large-history behavior has no dedicated automated test.
- iOS cannot read Apple Watch battery through a public API. The companion must be installed/opened at least once; unreachable Watch state is represented by the newest timestamped cache, not guaranteed live data.
- WatchConnectivity and watchOS background refresh timing are system-controlled. Simulator compilation does not validate paired-device transfer, complication scheduling, Shortcut results, or Watch energy impact.
- The track complication is not a second GPS recorder and is not guaranteed real time. It uses application context plus complication user-info delivery when budget/activation permit; it can still lag/coalesce under system scheduling, currently supports accessory-circular only, and displays at most four recent route segments with eight sampled points per segment.
